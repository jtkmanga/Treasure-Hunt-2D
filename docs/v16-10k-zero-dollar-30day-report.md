# รายงานความเป็นไปได้: Treasure Hunt 2D ผู้เล่นออนไลน์ 10,000 คน × 30 วัน โดยไม่จ่ายเงินเลย

วันที่ประเมิน: 3 พฤศจิกายน 2026

## คำตัดสินก่อนการทดสอบออนไลน์

**ยังไม่สามารถรับประกันได้ว่ารองรับผู้เล่น 10,000 คนที่เล่น Multiplayer อย่างต่อเนื่องตลอด 30 วันด้วยเงิน $0.** สำหรับการเคลื่อนไหวตามปกติ การจำลองทางคณิตศาสตร์แสดงว่าเกินขีดจำกัดคำขอฟรีหลายเท่าก่อนนับ CPU, Duration, การรับส่งข้อมูลกับโซนอื่น การเก็บเหรียญและแอปอื่นในบัญชีเดียวกัน

ข้อมูลจาก Cloudflare ที่ตรวจในวันที่ 3 พฤศจิกายน 2026:

- Durable Objects ที่ใช้ SQLite บน Workers Free: **100,000 request-equivalents/วัน**; ครอบคลุมการเชื่อมต่อ WebSocket, alarm, RPC, ข้อความขาเข้า การเกินโควตาจะทำให้คำขอประเภทนั้นล้มเหลว ไม่คิดค่าเกินแบบ Paid
- ข้อความ WebSocket **20 ข้อความที่รับเข้าเทียบเท่า 1 DO request** สำหรับการคิดโควตา/ราคา; การเชื่อมต่อใหม่หนึ่งครั้งยังมีต้นทุน Worker request และ DO request
- Workers Free: **100,000 HTTP/WebSocket upgrade requests/วัน** ทั่วบัญชี, ไม่ใช่ต่อ Worker
- WebSocket Hibernation ลดค่า Duration ตอน DO ว่างและสามารถพักได้ แต่ไม่ได้ยกเลิกจำนวนข้อความขาเข้า รวมทั้งไม่ทำให้การต่ออายุสถานะ/รักษาการแข่งขันเหรียญฟรีอย่างไม่มีข้อจำกัด

อ้างอิงอย่างเป็นทางการ:
- https://developers.cloudflare.com/durable-objects/platform/pricing/
- https://developers.cloudflare.com/workers/platform/limits/
- https://developers.cloudflare.com/durable-objects/best-practices/websockets/

## การทดสอบ 30 วัน (ไม่ยิง Cloudflare จริง)

รัน `npm run test:free-30days` และ `npm run capacity:free-30days` เพื่อจำลอง **10,000 คน × 30 วัน** โดยใช้รอบโควตาแยกทุก 24 ชั่วโมง (Cloudflare รีเซ็ต 00:00 UTC)

| สถานการณ์ | DO requests อย่างต่ำ/วัน (วันแรก) | เทียบกับ 100,000/วัน | ความหมาย |
|---|---:|---|---|
| 10K ต่อค้างไว้เฉย ๆ ไม่มีข้อความเลย | 10,000 | ผ่านด้านคำขอเท่านั้น | ไม่ใช่เกม Multiplayer ที่ทุกคนกำลังเล่น |
| 10K ต่อค้าง แต่เชื่อมต่อใหม่ 1 ครั้ง/วัน และโหลดโลก 1 ครั้ง/วัน | 30,000 | ผ่านด้านคำขอเท่านั้น | ไม่พิสูจน์ความเสถียร 30 วัน |
| ทุกคนส่งตำแหน่งทุก 60 วินาที | 730,000 | **ไม่ผ่าน** (7.3× วันแรก) | 720,000 เฉพาะข้อความ บวกการเชื่อมต่อ |
| 1% ของคนออนไลน์ (100 คน) เดิน ส่งทุก 3 วินาที | 154,000 | **ไม่ผ่าน** | ขนาดผู้เดินแค่ 1% ยังเกิน |
| 5% (500 คน) เดิน ส่งทุก 3 วินาที | 730,000 | **ไม่ผ่าน** | เกินต่อเนื่องทุกวัน |
| 0.5% (50 คน) เดิน ส่งทุก 3 วินาที | 82,000 | ผ่านด้านคำขอเท่านั้น | ต้องให้คนอีก 9,950 คนแทบไม่ทำอะไร |
| ทุกคนอัปเดตตำแหน่งทุก 10 นาที | 82,000 | ผ่านด้านคำขอเท่านั้น | ไม่เหมาะกับการเดินลื่นหรือการแข่งขันแบบเรียลไทม์ |
| 10K โหลดโลกผ่าน HTTP ทุก 60 วินาที | 14,410,000 | **ไม่ผ่าน Workers และ DO** | หนักกว่า WebSocket มาก |
| 10K เชื่อมต่อใหม่ทุก 2 ชั่วโมง | อย่างต่ำ 130,000 | **ไม่ผ่าน** | แค่ Worker upgrade ก็เกิน 100,000/วัน |

*ตัวเลขเป็นค่าประมาณต่ำสุดจากแบบจำลองสมมติฐาน ไม่ใช่ค่าที่วัดจากเซิร์ฟเวอร์ Cloudflare จริง และไม่ได้รวม Duration, CPU, Storage, fan-out, คะแนน, reset, App Check/Firebase, anti-cheat และค่าใช้จ่ายของบริการอื่น*

### ขอบเขตที่ดีที่สุดในทางทฤษฎี

หากผู้เล่น 10,000 คนเปิด WebSocket พร้อมกันครั้งเดียว (10,000 คำขอในวันแรก) และไม่มีคำขออื่นใดเลย:

- โควตา DO ที่เหลือ = 90,000 request-equivalents
- คิดเป็นข้อความ WebSocket ขาเข้าทั้งหมดสูงสุดในแบบจำลอง = 1,800,000 ข้อความ/วัน
- เฉลี่ยได้ 180 ข้อความต่อผู้เล่นต่อวัน = **หนึ่งข้อความทุก 480 วินาที (8 นาที)**

นี่ยังเป็นเพดาน *สูงเกินจริง* เพราะข้อมูลเกม การข้ามโซน การเข้าใหม่ของมือถือ การเก็บเหรียญและผู้ใช้คนอื่น ๆ ในบัญชี Cloudflare ต้องกินโควตาร่วมกัน

เกมแบบโลกเดียวที่ตรวจเหรียญ 200 เหรียญทั่วเซิร์ฟเวอร์, Lucky Box รางวัลสุ่ม, anti-cheat และการเคลื่อนไหวสมจริง จำเป็นต้องมีการตรวจ/ซิงก์มากกว่าตัวเลขนี้หรือยอมลดประสบการณ์อย่างมาก

## ทางเลือกที่ไม่หลอกว่า 10K คนกำลังเล่นได้ฟรีทั้งหมด

1. **คง Cloudflare Free ระหว่างพัฒนา:** จำกัด Closed Beta และวัดการส่งข้อมูลจริง, ลดข้อความตำแหน่งที่ไม่จำเป็น, ห้ามเขียนฐานข้อมูลทุกเฟรม, ใช้ Hibernation เมื่อผู้เล่นนิ่ง
2. **รักษาโลกเดียว แต่จำกัดผู้เล่นที่ใช้งาน Multiplayer แบบเรียลไทม์พร้อมกัน:** 50 คนที่เดินพร้อมกันทุก 3 วินาทีอาจอยู่ในโควตาคำขออย่างต่ำ (82K วันแรก) หากคนอื่น ๆ เชื่อมต่อค้างเฉย ๆ; ยังไม่ผ่านเงื่อนไข 10K คนที่ได้เล่นเต็มรูปแบบ
3. **P2P/WebRTC บางส่วน:** ช่วยกระจายข้อมูลภาพตัวละครไปยังอุปกรณ์ผู้เล่นเอง แต่ต้องใช้ signaling, NAT traversal/TURN ในบางเครือข่าย, กลไกความปลอดภัย, รับประกัน uptime และ server-authoritative coin claims. ไม่ควรใช้ P2P เป็นแหล่งตัดสินคะแนนจริง และไม่มีหลักประกันว่าโครงสร้างพื้นฐานจะไม่มีค่าใช้จ่าย
4. **หากต้องการ 10K คนเล่นอย่างเต็มรูปแบบตลอด 30 วัน:** ต้องให้ตัวเลขจริงกำหนดแผน Paid หรือเปลี่ยนทรัพยากร/ลดความถี่และฟีเจอร์อย่างโปร่งใส **ห้ามอ้างว่า $0 ผ่านแล้ว**
5. ห้ามปล่อยให้ระบบคะแนน การเก็บเหรียญและการซิงก์ล้มเหลวแบบเงียบ ๆ เมื่อเข้าใกล้ขีดจำกัด Free; แจ้งผู้ใช้และหยุดการให้รางวัลหรือจำกัดการรับผู้เล่นอย่างปลอดภัย

## ความปลอดภัยและขอบเขตงาน

- เครื่องมือคำนวณนี้ **ไม่ส่งคำขอไป Cloudflare**, ไม่สร้าง Durable Objects และไม่จำลอง WebSocket จริง 10,000 ตัว
- ไม่ Deploy เกม Staging/Production ไม่เปิด public score writes ไม่แก้ Payment ไม่ทำ Admin/PITR
- ผลลัพธ์ไม่รับรอง Duration / CPU / network / storage / Firebase quota / WebSocket stability / GitHub Actions account minutes
- ต้องมีการทดสอบ 100 → 1K → 10K จริงพร้อมตรวจโควตาและผลข้างเคียงจึงสรุปการเปิด Public ได้
